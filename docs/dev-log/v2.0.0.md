## 阶段 0 — v2 模块脚手架

**日期**：2026-10-02
**目标**：建立 v2 模块边界，使后续每个阶段都能独立编译与测试。

### 交付物

| 项 | 说明 |
|---|---|
| `go.mod` | module 路径改为 `github.com/tangthinker/user-center/v2`（Go modules 对 v2+ 的强制要求） |
| 依赖收敛 | 保留 `gofiber/fiber/v2`、`gorm.io/gorm`、`gorm.io/driver/sqlite`；**移除 `cockroachdb/pebble`** 与 `tangthinker/jwt-model` |
| 删除旧树 | `main.go`、`internal/**`、`pkg/**` 全部移除（按设计 §附录 A） |

### 决策与偏差

1. **保留 `go 1.22.6` 指令**（不随本机 1.25.4 升级）：宿主服务的 Go 版本不受本库牵制，避免为了新语法强制宿主升级。实现中不使用 1.23+ 的标准库 API。
2. **不再提供根 `main.go`**：库形态下没有独立进程；可运行示例放到阶段 6 的 `examples/`。
3. **模块路径带 `/v2`**：这会使宿主的 import 路径从 `github.com/tangthinker/user-center/pkg` 变为 `github.com/tangthinker/user-center/v2/pkg`。这是 Go modules 对主版本 ≥2 的硬性要求，无法规避；`RegisterUserCenter` / `TokenValid` 的**函数签名保持不变**，宿主只需改 import 行与 `go.mod` 一行。
4. **不引入第三方测试库**：单元测试只用标准库 `testing`，保持库的依赖面最小。

### 测试

```text
$ go build ./...        # 阶段 0 无代码，预期通过（空模块）
$ go test ./...         # 无测试文件
```

基线（改造前）供对照：旧树 3 个包有测试且全部通过（`idgen`、`pwdencry`、`model`、`service/auth`）。

## 阶段 1 — 存储层与迁移

**日期**：2026-10-02
**目标**：把"每宿主一份 SQLite(WAL)"与"版本化迁移 + schema 前向兼容"落到代码，并确保库初始化路径**不可能 panic**。

### 交付物

| 文件 | 内容 |
|---|---|
| `internal/domain/models.go` | 8 张表的 GORM 模型 + 领域常量（状态 / purpose / scope / 邮件状态）+ `NormalizeEmail` |
| `internal/migrate/migrate.go` | `Run(ctx, db)`、`LatestVersion()`、`ErrSchemaTooNew`；每个迁移独立事务、幂等可重入 |
| `internal/migrate/migrations.go` | schema v1 全量 DDL（含两个关键**部分唯一索引**） |
| `internal/store/store.go` | `Open(Config)` / `DB()` / `Path()` / `Close()`；DSN 参数、权限收敛、连接数控制 |
| `internal/store/store_test.go` | 11 个用例 |
| `internal/migrate/migrate_test.go` | 9 个用例 |

### 关键实现决策

1. **不使用软删除**：模型里没有 `DeletedAt`，因此 `ux_users_email` 是普通唯一索引即可，规避了设计 §8 坑 #1（"被软删用户永久占住邮箱"）。
2. **`MaxOpenConns` 默认 1**：SQLite 单写者模型下，把连接数压到 1 可从根本消除 `SQLITE_BUSY`；代价是丧失读并发，对个位数用户场景无影响。副作用是**事务内必须使用事务句柄**（`tx`），否则会自锁——已在 `Store.DB()` 的文档注释中明确要求。
3. **`uid` 用部分唯一索引**：`CREATE UNIQUE INDEX ux_users_uid ON users(uid) WHERE uid IS NOT NULL`，使"多个待激活用户（uid 为 NULL）共存"与"非 NULL 必唯一"同时成立，且依赖 SQLite 默认 `BINARY` collation 实现**大小写敏感**。
4. **`ux_otp_active` 同理**：`(email, purpose) WHERE consumed_at IS NULL` 唯一，把"同一邮箱同一用途至多一个有效码"（不变量 I4）交给数据库保证，而不是靠应用层自觉。
5. **`invitations` 增加 `check_count` 列**（相对设计文档的 DDL）：`check-uid` 的每 token 20 次限制需要一个原子计数器，放在邀请行上比旁路表更简单。v1 尚未发布，属于发布前调整，不构成破坏性变更。
6. **`mail_outbox` 预留 `priority` 列**：本期不参与调度，为将来可能的优先级队列留出零成本升级路径（设计 §7.2）。
7. **GORM 日志被丢弃**（`logger.Discard`）：库不接管宿主的日志输出（L5）。
8. **时间统一 UTC**：`NowFunc` 强制 UTC，避免 SQLite 时间字符串比较受时区/夏令时影响。

## 阶段 2 — 领域服务

**日期**：2026-10-02
**目标**：把设计中的"原子性要求"逐个落到 SQL 层面，并让每个安全不变量都有对应测试。

### 交付物

| 文件 | 内容 |
|---|---|
| `internal/secure/secure.go` | 令牌生成（32B `crypto/rand`）、sha256、数字验证码、绑定 purpose+email 的 HMAC、恒定时间比较、邮箱短哈希 |
| `internal/uidrule/uidrule.go` | uid 规则：大小写敏感 / 3–32 / 字母打头 / `[A-Za-z0-9_-]` / 保留字**大小写不敏感** |
| `internal/session/session.go` | `Issue` / `Verify`（含续期）/ `Revoke` / `RevokeAllForUser` / `ListForUser` / `DeleteExpired` |
| `internal/otp/otp.go` | `Issue`（含冷却复用）/ `Verify`（原子递增 + 单次消费）/ `DeleteExpired` |
| `internal/invite/invite.go` | `Create`（作废旧邀请）/ `Lookup`（只读）/ `RecordUIDCheck`（带上限的原子计数）/ `UIDAvailable` / `Consume`（原子激活） |
| `internal/ratelimit/ratelimit.go` | 邮箱与全局维度（SQLite）+ IP / verify / admin 维度（进程内窗口） |
| `internal/audit/audit.go` | 审计写入 + **凭据键名黑名单硬拦截** + 查询 + 清理 |
| `internal/store/errors.go` | `IsUniqueViolation`（驱动错误码优先，字符串判断仅作退化） |
| `internal/testsupport/testsupport.go` | 临时库、用户构造、可推进时钟 |

### 关键实现决策

1. **`WithTx` 模式**：所有服务都提供 `WithTx(tx)` 返回绑定同一事务的副本，编排层用它在一个事务内组合多个服务。这是 `MaxOpenConns=1` 下的必要约定（否则自锁）。
2. **验证码尝试次数用单条 SQL 原子完成**：
   ```sql
   UPDATE otp_codes
   SET attempts = attempts + 1,
       consumed_at = CASE WHEN attempts + 1 >= ? THEN ? ELSE consumed_at END
   WHERE id = ? AND consumed_at IS NULL AND attempts < ?
   ```
   并发试码无法突破上限（对照设计验收 #13）。
3. **邀请消费是"两步条件更新 + 受影响行数判定"**：先消费 token（`consumed_at IS NULL`），再激活用户（`status='invited' AND uid IS NULL`）。任一步受影响行数 ≠ 1 即回滚。uid 冲突由唯一索引裁决并映射为 `ErrUIDTaken`。
4. **uid 冲突不消耗邀请**：测试证明 uid 被占用时用户仍可用另一个名字激活（否则用户会因一次撞名永久失去邀请）。
5. **冷却期复用实现为"不返回明文码"**：服务端只有 HMAC，无法重发明文，因此 `Issued.Code == ""` + `Reused == true` 就是"不要再发邮件"的信号。这一条同时实现了"省配额"与"防骚扰"。
6. **限流计数的是请求数而非实际发信数**：有意偏保守；`mail_log` 同时记录被拒绝的请求（`accepted=0`），既供观测又不占配额。
7. **审计的凭据拦截**：`detail` 序列化后递归检查键名（`token` / `code` / `password` / `secret` / `*_token` / `*_hmac` 等），命中即返回 `ErrDetailRejected`，把"误把凭据写进审计表"从静默事故变成显式错误。

## 阶段 3 — 邮件子系统

**日期**：2026-10-02
**目标**：把"宿主注入 Mailer + 持久化 outbox + 幂等模板渲染"落地；并让"队列不丢信、不重发、可观测"成为可测行为。

### 交付物

| 文件 | 内容 |
|---|---|
| `internal/mail/mailer.go` | `Mailer` 接口、`Message`、`Hooks`（OnSent/OnFailed/OnWorkerError）、`ErrDuplicate`、`ErrPermanent` |
| `internal/mail/address.go` | `ValidateAddress`（含 CR/LF 与控制字符拦截）、`sanitizeHeader` |
| `internal/mail/rfc822.go` | `BuildRFC822`：头部构造、RFC 2047 主题编码、base64 正文、multipart/alternative、Message-ID |
| `internal/mail/smtp.go` | `SMTPConfig` / `NewSMTP` / `Send`：隐式 TLS(465) 或 STARTTLS，拒绝明文信道认证 |
| `internal/mail/templates.go` | `Renderer` 接口、`DefaultRenderer`（7 个模板）、payload 结构与 `EncodePayload` |
| `internal/mail/outbox.go` | `Enqueue`（幂等）/ `ProcessOnce` / `Run` / `Stats` / `CleanupSent`、退避重试、原子抢占 |

### 关键实现决策

1. **入队放在业务事务内（outbox 模式）**，相对设计文档"提交后入队"是**有意的改进**：事务提交则邮件必在队列，回滚则不会有幽灵邮件；崩溃窗口从"可能丢信"缩小到"不可能丢信"。设计文档 §7.3 的措辞已在阶段 7 同步。
2. **`ErrPermanent` 不重试**：模板损坏、地址非法这类错误直接进终态，不浪费 5 次重试额度。
3. **头部注入防护**：`To` / `Subject` / `FromName` 中的 CR/LF 一律拒绝；邮箱地址另做结构校验（唯一 '@'、域名含点、无空白/控制字符）。
4. **验证码不进主题**：模板层保证，并有专门测试守护。
5. **SMTP 不提供"不安全兜底"**：`Username` 非空且连接未加密时直接拒绝认证（除非显式打开 `AllowPlainAuthWithoutTLS`，默认关闭）。
6. **`EncodePayload` 接受已编码的 `[]byte`**：编排层常常先编码一次，二次编码会把 JSON 变成 base64 字符串——这在开发中被测试当场抓到（7 个用例同时失败），已固化为行为并有注释。

## 阶段 4 — 编排层（用例层）

**日期**：2026-10-02
**目标**：把领域服务组合成完整业务动作，保证"一个业务动作 = 一个事务"，并把 §6.6 的错误语义固化下来。

### 交付物

| 文件 | 内容 |
|---|---|
| `internal/user/user.go` | 用户仓储：创建（invited/active）、按邮箱/uid/id 查询、状态与角色、改邮箱、删除、统计、`MarkLogin`（原子判定首次登录） |
| `internal/app/app.go` | `Config`/`New`、语义化错误集、`RateLimitedError`、`Bootstrap`、`WithTx` 辅助、UA 摘要 |
| `internal/app/usecases_public.go` | `RequestLoginCode` / `RequestAdminLoginCode` / `VerifyLoginCode` / `VerifyAdminCode` / `VerifySession` / `VerifyUserSession` / `Logout` / `GetInvite` / `CheckUID` / `AcceptInvite` |
| `internal/app/usecases_admin.go` | `AdminCreateUser` / `AdminResendInvite` / `AdminRegenerateInviteLink` / 列表 / 启停 / 改邮箱 / 踢会话 / 删除 / 审计查询 / `AdminStats` |
| `internal/app/app_test.go` | 21 个端到端用例 |

### 关键实现决策

1. **一个业务动作一个事务**：建用户 + 签发邀请 + 入队邮件 + 写审计在同一事务内（outbox 模式）；激活、改邮箱、停用同理。测试验证了"事务提交 ⇒ 邮件必在队列"。
2. **`VerifyUserSession` 与 `VerifySession` 分离**：管理会话**不能**当普通用户会话使用（`scope=admin` 一律拒绝）。这是一条关键越权防线：否则管理员登录会顺带获得宿主所有用户资源的访问权。
3. **登录失败语义统一**：邮箱不存在 / 未激活 / 验证码错 / 非管理员走 admin 登录 —— 全部返回 `ErrInvalidCredentials`，对外不可区分。
4. **未注册邮箱也消耗限流额度**：`RequestLoginCode` 对未知邮箱照样记账，避免"用未注册邮箱白嫖探测"。
5. **`AdminRegenerateInviteLink` 不发邮件**（复制链接场景），`AdminResendInvite` 发邮件；两者都作废旧链接并写不同审计动作。
6. **最后管理员保护**：不能停用/删除最后一个管理员（防止把自己锁在门外）。
7. **邮件 payload 发送成功后清空**：邀请链接与验证码的明文只应存在于"待发"期间；终态失败同样清空。
8. **冷却期零值语义修正**：`otp.Config.Cooldown` 的零值现在取默认 60 秒（安全默认），显式关闭需传负数。这是测试当场发现的问题（`TestRequestLoginCodeCooldownReuse` 失败暴露了"忘配置就不冷却"）。

### 测试

**日期**：2026-10-02
**目标**：把用例层暴露为 HTTP，落地"状态码正确 + 文案统一 + 管理面 fail-closed"。

### 关键实现决策

1. **保留 `{code,msg,data}` 信封，但补齐状态码**：这是对审计结论 P1-4（"认证失败也返回 200"）的直接修复——客户端形状不变，网关/WAF/监控却终于能看到 401/403/409/410/429。
2. **落地页由服务端渲染，GET 保持只读**：页面直接携带邮箱与有效期，省掉一次往返；`GET` 不消费 token，邮件安全网关预取不会烧掉邀请。页面带严格 CSP（`default-src 'none'`）、`no-store`、`no-referrer`、`noindex`。
3. **管理面双重本地校验 + 同源校验**：
   - `LocalOnly` 只认 `RemoteAddr`（回环）+ `Host` 白名单（挡 DNS rebinding）；**绝不读 X-Forwarded-For**；
   - `SameOriginOnly` 在带 `Origin` 时要求与 `Host` 同源（浏览器外客户端不带 Origin，直接放行）；
   - 管理令牌走 `Authorization: Bearer`，界面不使用 cookie ⇒ 无环境凭据、无 CSRF 面。
4. **`failStatus` 的返回值陷阱（本阶段实测抓到）**：`c.JSON()` 成功时返回 **nil**，而 Fiber 的处理器链以"返回 nil 且未调用 `Next()`"表示继续执行下一个处理器。最初的 `requireAdmin` 写成"写完 401 再 `return failStatus(...)`"，导致**鉴权失败后业务处理器照样执行，并用 200 覆盖 401**（实测：无令牌请求 `/admin/users` 返回了完整用户列表）。修复方式：前置检查改为返回 `bool`，"已拒绝"时显式 `return nil` 终止链。
5. **资源按白名单提供**：静态资源用显式 switch 提供固定文件，不做目录遍历，天然免疫路径穿越。
6. **`AdminListSessions` 对不存在的用户返回 404**（而非空列表），让接口语义准确。

## 阶段 7 补充二 — 真实发信暴露的两个问题

**日期**：2026-10-02
**触发**：用阿里企业邮箱向 `@yeah.net` 发信，日志持续报
`mail: auth: 526 Authentication failure[0]`，且**每封邮件都在退避重试**（第 1 次、第 2 次…）。

### 定位

`526 Authentication failure` 是**阿里邮箱官方定义的认证失败码**（[官方文档](https://help.aliyun.com/zh/document_detail/602363.html)），
官方列出四个原因：① SMTP 用户名必须是完整发信邮箱地址且无多余空格；② SMTP 密码——
*未开启*三方客户端安全密码时用**登录密码**，*已开启*时必须用**新的安全密码**；
③ 服务器地址/端口不对；④ 访问策略（SMTP 协议未开启、策略不覆盖该地址、限制来源 IP、频率 >10 次/秒）。

> 我最初把它当成网易专属错误码（网易确实也用 526），据此写死了"必须用三方客户端安全密码"的提示——
> **这是错的**：在管理员未开启该功能时，正确口令恰恰是登录密码。已按官方四点改写。

### 两个代码修复

1. **5xx 不再重试**：新增 `permanentIf5xx`，依据 RFC 5321 把 5xx（认证失败、550 用户不存在、
   552 超配额）标记为 `ErrPermanent`，立即进入终态；4xx（灰名单、421 服务不可用）仍走退避重试。
   此前"配置错误"会白等 1 分钟 → 5 分钟 → 15 分钟 → 1 小时 → 6 小时，并把队列堆满注定失败的邮件。
   `RCPT TO` 原本被无条件当成永久错误，也一并改为按响应码判定。
2. **错误文案可自诊断**：认证失败信息现在包含 `服务器:端口`、用户名、服务端原始响应码，
   以及**按服务商区分的排查清单**（阿里 / 网易 / 腾讯 / Gmail / Outlook / 其他）。

修复后的错误长这样：


## 阶段 7 补充九 — 可配置的应用图标（web app icon）

**日期**：2026-10-02
**要求**：能否给 web 管理端设置 app icon。

### 先摆清两种做法

| 做法 | 形态 | 代价 |
|---|---|---|
| **A. 宿主注入（本次实现）** | `Config.AppIcon` 传字节，库在**同源**路径提供，同时作 favicon 与界面标识 | 换图标要重新部署 |
| B. 运行时上传 | 管理面板加"上传图标"接口，入库、动态下发 | 需要 schema 迁移 + 上传接口 + 类型/体积校验 + 审计；图标变成又一项被管理的数据 |

先做 A：它是库的正确形态（资源由宿主配置注入），且把路由固定为 `<assets>/icon`——
将来若要加 B，前端与路由都不用改，只换字节来源。

### 关键设计决定：为什么传**字节**而不是 URL

宿主常把静态资源挂在**另一个监听**上（管理面 `127.0.0.1:9998`、公开面 `127.0.0.1:9999`）——
**不同端口即不同源**，`<img src="http://127.0.0.1:9999/static/icon.png">` 会被本页 CSP 直接拦掉。
由库在同源路径下提供字节，既不用放宽 CSP，也不依赖宿主的部署拓扑。

### 实现

| 位置 | 内容 |
|---|---|
| `internal/httpapi/icon.go` | `Icon` 类型与 `NewIcon(raw, declared)` 校验：类型白名单（PNG/JPEG/WebP/GIF/ICO）+ **魔数复核**（声明成 PNG 实际不是图片也拦）+ 256 KiB 上限；`serveIconBytes`；`pageCSP`（`img-src 'self'`） |
| 管理面 / 公开面 | 新增 `<assets>/icon` 路由；页面注入 `{{FAVICON}}`/`{{APP_MARK}}`/`{{APP_MARK_SM}}`，有图标用 `<img>`、没有则退回服务名首字方块 |
| `usercenter.Config` | `AppIcon []byte` + `AppIconContentType string`；`Validate()` 与其构造路径都会提前校验——**非法图标在启动时报错**，不拖到浏览器请求 |
| `internal/webui` | `.app-mark--img` / `.toolbar__mark--img` 去掉方块底色；模板改用服务端生成的标识 |
| `examples/demo` | 新增 `-icon <path>` 参数 |

### 明确不支持 SVG

SVG 可以携带脚本，而图标是**会被直接导航打开的地址**（用户手动输入 `/admin/assets/icon`）。
因此拒绝 SVG，并且**无论宿主是否声明类型**都按内容识别、给出可执行的报错：

```

```

## 阶段 7 补充十 — 会话续期阈值按 scope 修正（回答"token 时效与续期怎么设计"）

**日期**：2026-10-02
**触发**：提问"现在 token 的时效、续期是如何设计的？"

### 梳理出的三套时效

| | 会话 token | 登录验证码 | 邀请 token |
|---|---|---|---|
| 有效期 | 用户 idle 7 天 / absolute 30 天；管理员 idle 30 分钟 / absolute 8 小时 | 登录 10 分钟 / 管理员 5 分钟 | 7 天 |
| 续期 | 仅当 `idle 剩余 < 阈值` 时推到 `now+idleTTL`，被 absolute 截断 | 无（60 秒冷却内复用同一个码，不重发） | 无（单次消费 + 每 token 限查 20 次） |

### 发现并修复的缺陷：续期阈值没有按 scope 取值

`Config.RenewWindow` 只有**一个**全局值，默认 `IdleTTL/2 = 3.5 天`；而管理会话 idle 只有 30 分钟，
于是判定"剩余 < 3.5 天"**永远成立** ⇒ 管理员每点一次页面就写一次库（实测确认：剩余 29 分钟时即写库）。

修法：新增 `AdminRenewWindow`（默认 `AdminIdleTTL/2 = 15 分钟`），`renewWindowFor(scope)` 分 scope 取值。

**修复过程中又踩到第二个坑**：`withDefaults()` 里我把 `AdminRenewWindow` 的推导写在了
`AdminIdleTTL` 补默认值**之前**，于是阈值恒为 0 → "剩余不足 0"永远成立 → 管理会话**永不续期**、
30 分钟必定掉线（比原缺陷更糟）。已把 `withDefaults` 的顺序改为：先补全两个 scope 的基准 TTL，
再推导各自阈值，并在代码里写明"顺序很关键"。

修正后的实测（探测日志）：

```text
issued              now=00:00 idle=00:30 last=00:00
verify @+1m         now=00:01 idle=00:30 last=00:00   ← 剩余 29 分钟 ≥ 阈值 15 分钟：不写库
verify @+20m        now=00:20 idle=00:50 last=00:20   ← 剩余 10 分钟 < 阈值：续期到 now+30m
```

### 新增测试（2 个）

| 用例 | 守护 |
|---|---|
| `TestRenewWindowIsPerScope` | 管理会话剩余 29 分钟不写库、剩余 10 分钟才续期；用户会话剩余 6 天不写、剩余 3 天续期 |
| `TestCustomRenewWindows` | 宿主自定义阈值同样按 scope 生效（剩余 3 小时 > 阈值 2 小时 → 不续期） |

### 顺带记录两条设计取舍（非缺陷）

1. **续期失败不影响校验**：`maybeRenew` 的错误被吞掉（`_ = err`），可用性优先，下次请求再试——
   代价是"续期写失败时可能提前掉线"，而不是"校验直接失败"。
2. **`last_seen_at` 只在续期时更新**：因此它的粒度等于续期阈值（用户会话最粗 3.5 天）。
   它用于审计与趋势判断，不能当作精确的"最近活跃时间"。

## 阶段 7 补充十一 — 会话期限对客户端可见 + 一次时钟混用的修复

**日期**：2026-10-02
**触发**：提问"快到期时能不能用老 token 换新 token / 要不要 refresh token"。

### 先补的短板：客户端此前**看不到**期限

任何"到期前处理"的方案都要求客户端知道还剩多久，而 `/session/verify` 原本只返回 `uid` 与 `scope`。
现在一并返回：

```json
{ "uid": "alice", "scope": "user",
  "expires_at": "2026-01-08T00:00:00Z",          // idle 期限
  "absolute_expires_at": "2026-01-31T00:00:00Z", // 硬上限
  "idle_seconds_left": 604800,
  "absolute_seconds_left": 2592000 }
```

### 顺带修掉一处时钟混用

第一版在 handler 里写了 `time.Now()`，而库本身有**可注入时钟**（`app.Now()`）。测试用假时钟签发会话、
真实时钟算倒计时，得到 −26,000,000 秒（约 −300 天）——测试当场变红。已改为统一走 `p.app.Now()`。
这不只是测试问题：宿主注入时钟（演练、受控环境）时，混用时钟源会让接口返回的倒计时与实际校验结果互相矛盾。

### 关于"到期前换新 token"与 refresh token 的结论

**不建议**用"老 token 直接换新 token"来延长会话：那等于删掉 `absolute` 的全部意义，
而 `absolute` 正是"到期必须重新证明一次身份"的节拍器（v1 的缺陷就是无上限的滑动续期）。

也不建议为这个问题引入 refresh token：它解决的是另一个问题（缩短访问令牌暴露窗口 + 被盗检测），
并不能让绝对期限消失——refresh 链同样需要上限，否则就是永续。

三条可行路线与取舍见对话中的分析；如需实现"带约束的轮换"，需要：`sessions` 加
`chain_id`/`generation`/`rotated_from`（schema 迁移）、交换接口、链上限、并发交换的宽限处理、以及审计。

## 阶段 7 补充十二 — 邮件里的时间不再只写 UTC：显示时区可配置

**日期**：2026-10-04
**触发**：管理员登录通知显示 `时间：2026-10-04 04:13:12 UTC`，而本人是北京时间中午 12:13 登录的——
"12 点显示 4 点，有点太离谱了"。

### 先定性：时钟是对的，**显示**不对

同一条通知邮件的 `Date:` 头被邮件客户端换算成了本地时间 12:13（截图上就是 12:13），
说明库取到的时刻本身没错：`2026-10-04 04:13:12 UTC` 就是北京时间 `12:13:12`。
错的是正文那一行——`humanTime` 里写死了 `.UTC()`：

```go
return t.UTC().Format("2006-01-02 15:04:05 UTC")   // ← 收件人只能自己 +8 小时
```

这类 bug 的特点是**没人会报障**：时间戳格式完全合法，只是会被默默读错（"我中午登录的，
怎么写着凌晨 4 点"）。对一个"有人登录了管理界面"的安全通知来说，这尤其致命——
收件人第一反应是"这不是我"，第二反应才是去算时差。

### 改法：显示时区可配置，并且必须带上偏移

- `Config.TimeZone`（宿主）/ `RendererConfig.TimeZone`（渲染器）：IANA 时区名，
  **留空 = 跟随宿主进程的本地时区**（`time.Local`），写错在 `New` 阶段直接报错；
- 正文里的时间统一渲染成 `2026-10-04 12:13:12 +08:00`：**偏移量是刻意保留的**，
  它是收件人唯一能自查"这封邮件用的是不是我这里的时区"的线索，也方便和 UTC 日志对齐；
- 同一时区贯穿所有"给人看的时间"：登录通知、操作通知、邀请链接失效时间（邮件正文 + 落地页）；
- 管理界面/API 里本来就是 RFC 3339（带 `Z`），由浏览器换算，不受这项配置影响；
  但 `CreateUserResult.ExpiresAt` 此前是 `"2006-01-02 15:04"` 的 **UTC 墙上时间**，
  看着像本地时间、实际少 8 小时，已改成 RFC 3339 并让前端 `shortTime()` 按浏览器时区显示；
- 兜底嵌入 `time/tzdata`：最小化容器（scratch/distroless）里没有 `/usr/share/zoneinfo`，
  否则 `TimeZone: "Asia/Shanghai"` 会在启动时报错，宿主只能在"起不来"和"继续显示 UTC"之间二选一；
- 演示程序加 `-tz` 参数，并在启动时打印一行「时间显示时区: Asia/Shanghai（现在是 … +08:00）」——
  时区写错不会有人报障，只会被默默误解，所以让它可见。
